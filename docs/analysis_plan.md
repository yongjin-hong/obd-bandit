# 분석 계획: Open Bandit Dataset 기반 밴딧 알고리즘 시뮬레이션

> 최종 수정: 2026-11-03 (시뮬레이션 설계 완료, 구현 전)

## 1. 데이터

### 무엇인가
- **Open Bandit Dataset (OBD)**: 일본 패션 이커머스 ZOZOTOWN의 추천 영역에서 수집된 실제 로그
- 두 추천 정책(**Random**, **Bernoulli Thompson Sampling(BTS)**)을 A/B 테스트로 동시에 운영하며, 사용자에게 무엇을 보여줬고 클릭했는지 기록
- 2019-11-24 ~ 2019-11-30, 7일간 수집
- 출처: [research.zozo.com/data.html](https://research.zozo.com/data.html) (전체 버전), `obp` 패키지 내장 (소용량 버전)

### 구성
| 구분 | 내용 |
|---|---|
| 파일 단위 | 로깅 정책(random, bts) × 캠페인(all, men, women) |
| 1행 | 노출 1건 |
| 행동 | `item_id` (men 기준 0~33, 34개), `position` (슬롯 1~3) |
| 결과 | `click` (0/1) |
| 컨텍스트 | `user_feature_0~3` (해시된 범주형 4개), `user-item_affinity_*` (아이템 수만큼) |
| 정책 정보 | `propensity_score` (random은 전 행 1/34) |
| 별도 파일 | `item_context.csv`: `item_feature_0` (수치형), `item_feature_1~3` (해시된 범주형) |

### 사용 데이터 (men 캠페인, 전체 버전)
| 로그 | 원본 행 수 | 중복 제거 후 | 클릭률 (중복 제거 후) |
|---|---|---|---|
| random | 452,949 | 452,868 | **0.4946%** |
| BTS | 4,077,727 | 4,076,779 | **0.6528%** (Random 대비 1.32배) |

### 데이터 정리 규칙
- 이름 없는 인덱스 컬럼 삭제, `timestamp`를 datetime(UTC)으로 변환
- **중복 행 제거**: 동일 시각·아이템·슬롯·클릭이 반복 기록된 행(전부 클릭=1, 클릭 로그 중복으로 추정)을 1행만 남김. random·BTS 모두 적용
- **아이템 피처는 전체 버전 파일 사용**: 소용량 버전과 범주형 해시값이 다름 (수치형은 동일)

## 2. 어떤 분석을 하는가

random 로그를 시간순으로 재생(**replay**)하며, 밴딧 알고리즘이 **실시간으로 학습하는 과정을 시뮬레이션**한다.

- **replay 원리**: 알고리즘이 고른 아이템이 로그의 아이템과 일치할 때만 결과를 기록하고 학습. random 로그는 모든 아이템이 1/34 확률로 노출되었으므로, 일치한 행들은 편향 없는 표본이 됨
- **BTS 로그는 replay에 쓰지 않음**: 아이템 선택이 균등하지 않아 편향이 생김. 실제 운영 성과(참고용 기준선)로만 사용

### 비교 정책
| 구분 | 정책 | 역할 |
|---|---|---|
| 비컨텍스추얼 | **Bernoulli TS** (replay) | 같은 조건에서의 BTS. 컨텍스트 미사용 |
| 컨텍스추얼 | **LinTS** (replay) | 사용자 피처 사용 |
| 검증용 | Random (replay) | 시뮬레이터 버그 체크. 실제 로그 클릭률(0.4946%)이 재현되는지 1회 확인. 비교표에는 미포함 |

- 두 정책 모두 Thompson Sampling 계열 → 차이는 **사용자 피처 사용 효과**로 해석

### 비교 구조
| 비교 | 의미 |
|---|---|
| **LinTS vs Bernoulli TS** | **핵심 비교.** 같은 조건에서 사용자 피처를 쓴 효과 |
| 두 정책 vs Random 로그 (0.4946%) | 학습 효과가 있었는가 (하한선) |
| 두 정책 vs BTS 로그 (0.6528%) | **참고용.** 학습량이 다르고, ZOZO는 사전 설정(warm start)으로 운영해서 직접 비교는 공정하지 않음 |

### 구현 방식
- `obp`는 **소용량 데이터 제공 용도로만** 사용
- 피처 구성, replay 시뮬레이터, 정책은 **numpy·polars로 직접 구현**

## 3. 왜 하는가

### 상황 설정
추천팀은 현재 BTS를 운영 중이다. 사용자 정보를 활용하는 컨텍스추얼 밴딧으로 교체하면 효과가 있을지 궁금하지만, 새 알고리즘마다 A/B 테스트를 돌리는 것은 비용과 리스크가 크다.

### 목적
- 실제 배포 없이 로그만으로 **알고리즘 교체 가치를 사전에 판단**
- 사용자 피처 활용(컨텍스추얼)이 실제로 효과가 있는지 확인

### 분석 질문
- 같은 조건에서 LinTS가 Bernoulli TS보다 클릭률이 높은가? (사용자 피처의 효과)
- 두 정책이 Random보다 나은가? BTS 실제 운영 성과와는 어느 정도 거리가 있는가?
- 학습은 얼마나 빨리 수렴하는가?

## EDA 결과 요약 (men, random, 전체 버전)

### 슬롯
- 클릭률 1번 0.525% > 2번 0.503% > 3번 0.456%
- 1번과 3번의 신뢰구간이 거의 겹치지 않는 수준. 위치 효과는 있을 수 있으나 작음

### 아이템
- 아이템별 클릭률 0.32% ~ 0.75% (최대 약 2.4배)
- 상위와 하위의 신뢰구간이 겹치지 않음 → **아이템 간 차이는 실제로 존재**
- 상위 아이템(13, 31, 3번 등)은 BTS 기준선보다 높지만, 신뢰구간이 기준선을 포함

### 사용자 피처
- 범주 수: `user_feature_0~3` = 4 / 6 / 11 / 10개. 분포가 크게 치우쳐 있고 희귀 범주(비중 1% 미만) 존재
- `uf0_1 = uf1_1 = uf2_0 = uf3_0`은 동일 사용자 집단 (노출의 29%). 의미는 해시 처리로 알 수 없음
- `uf0_1` 클릭률 0.640% vs 나머지 약 0.45%로 확실히 높음
- 사용자-아이템 친밀도는 0이 아닌 값이 0.17%로 매우 희소

### 컨텍스추얼 밴딧의 근거
- `uf0_0`(61%)과 `uf0_1`(29%)의 아이템 선호 순위 상관이 0.36으로, 노이즈만으로 기대되는 최대치(약 0.67)보다 크게 낮음
- 상위 5개 아이템 중 겹치는 것은 1개뿐 → **두 그룹의 취향이 실제로 다름**
- 그 외 작은 그룹들은 데이터 부족으로 선호 차이를 판단할 수 없음

## 시뮬레이션 설계

### 평가 방식: replay(A) 먼저, 모델 기반 시뮬레이터(B)는 나중에
| 방식 | 클릭 결과 | 장점 | 한계 |
|---|---|---|---|
| A. replay | 실제 클릭만 | 편향 없음 | 일치할 때만 학습 → 학습량 적음 |
| B. 모델 기반 | 클릭 확률 모델로 생성한 가상 클릭 | 학습량 제한 없음, 수렴 과정 관찰 가능 | 환경 모델의 정확도에 좌우됨 |

- B를 구현할 때는 환경 모델을 밴딧과 다른 종류(예: 트리 기반)로 만들어 공정성 확보

### 슬롯 처리
- **기본: 슬롯 무시.** 각 행을 독립 라운드로 보고 아이템 1개 선택
- random 로그에서는 슬롯 배정도 무작위라 편향 없음 (노이즈만 약간 증가)
- 변형 실험: 슬롯 번호를 컨텍스트로 추가

### 입력 구조 (LinTS, 82차원 공유형 모델)
| 구간 | 차원 | 내용 |
|---|---|---|
| ① 사용자 피처 원-핫 | 26 | 희귀 범주(노출 비중 1% 미만)는 피처별 "기타"로 묶음. 인코딩 기준은 전체 random 로그 |
| ② 아이템 피처 | 28 | `item_feature_0` 수치 그대로 (1) + `item_feature_1~3` 원-핫 (7 + 16 + 4) |
| ③ `uf0_1` × 아이템 피처 | 28 | 사용자가 `uf0_1`이면 ②와 같은 값, 아니면 0 |

- 라운드마다 후보 아이템 34개 × 82차원 행렬을 만들어 점수 계산 → 최대값 선택
- 모든 라운드의 데이터가 하나의 가중치에 모임 → 데이터 효율 확보
- 아이템 원-핫 대신 아이템 피처 사용: 비슷한 아이템끼리 정보 공유. 피처가 같은 아이템은 이 데이터에서 구분할 필요가 없다고 봄
- 상호작용은 EDA에서 선호 차이가 확인된 `uf0_1` 하나만 사용 (파라미터 수 억제)
- 제외: 사용자-아이템 친밀도 (희소), 슬롯 (기본 설정)
- 클릭 여부(0/1)를 선형 모델로 예측하는 표준 방식. 정규화 강도 1로 고정

### 기간 분리와 반복 실행
| 구분 | 기간 (UTC) | 용도 | 예상 클릭 |
|---|---|---|---|
| 조정 | 11/24 ~ 11/25 (일~월) | LinTS 하이퍼파라미터 선택 | 약 19건 |
| 평가 | 11/26 ~ 11/30 (화~토) | 최종 성능 비교 | 약 47건 |

- 조정 기간에서 얻는 것은 **설정값**뿐. 평가 기간에는 정책을 **처음부터 다시 학습**
- **반복 실행**: 로그 순서를 섞어 20~30회 반복 → 평균과 95% 구간
- LinTS 조정 후보: 분산 크기 0.1 / 0.5 / 1.0 (클릭이 적어 조정은 대략적인 방향 선택 수준)
- Bernoulli TS: 사전분포 Beta(1,1), 조정 없음

### 평가 지표
- **replay 클릭률**: 일치 라운드의 평균 클릭률 (반복 실행 평균, 95% 구간)
- **누적 클릭률 추이**: 학습 속도
- **일치 라운드 수**: 추정값의 신뢰도

### 코드 구조
| 파일 | 내용 |
|---|---|
| `src/bandit.py` | ① 피처 구성 (사용자 피처 인코더, 아이템 피처 행렬, 후보 행렬 생성) ② 정책 (`RandomPolicy`, `BernoulliTS`, `LinTS`, 공통 사용법 `select` / `update`) ③ 시뮬레이터 (replay 실행, 반복 실행) |
| `notebooks/01_eda.ipynb` | EDA |
| `notebooks/02_simulation.ipynb` | 데이터 로딩·정리 → 기간 분리 → Random 검증 → LinTS 조정 → 평가 반복 실행 → 결과 비교·시각화 |

- 아이템 피처 대신 아이템 원-핫 사용

- 다른 정책 추가: LinUCB, ε-greedy 계열, `uf0_1` / 나머지로 나눈 세그먼트별 Bernoulli TS
- 상호작용 범위 확대 (`uf0_2`, `uf1_3`, `uf3_4` 등 클릭률이 뚜렷이 다른 범주)

### 리스크와 한계
- **클릭 부족**: 평가 기간 예상 클릭 약 47건. 정책 간 차이를 통계적으로 구분하기 빠듯함 → 반복 실행으로 분산 파악, 이후 모델 기반 시뮬레이터로 보완
- **replay는 짧은 학습 구간만 평가**: 실제 운영이라면 모든 노출에서 학습하지만, replay는 약 1/34만 학습 → 덜 학습된 상태의 비교
- **데이터 스누핑**: 상호작용 피처(`uf0_1`)를 평가에 쓰는 같은 random 로그의 EDA로 선택 → LinTS가 실제보다 유리하게 나올 수 있음
- **BTS 로그와의 비교 한계**: 학습량과 사전 설정이 달라 참고용으로만 사용
- **정상성 가정**: 로그 순서를 섞으므로 기간 중 사용자 행동이 변하지 않는다고 가정
- **해석 한계**: 피처가 해시 처리되어 있어 그룹과 아이템 특징의 실제 의미는 알 수 없음
